# Casdoor 功能更新与公司公告

将提交记录转成同事能理解的“更新了什么、有什么用、在哪里使用”。默认读者为公司全体员工，组织管理员、系统管理员和应用接入人员的更新放在独立补充区。默认交付功能清单与公告草稿，不执行部署或发送。

## 确定版本范围

- 在用户当前指定的 Casdoor 仓库执行，先读取适用的 AGENTS.md 及项目约定。不要硬编码机器路径、分支、公司名称或生产地址。
- 优先使用用户给出的旧版本和新版本，解析为完整提交 SHA；其次使用指定分支及日期。未指定范围时分析当前 HEAD 最近一个月的更新，并明确 HEAD 只是代码版本。
- “最近一个月”默认从用户所在时区的当日向前推一个日历月，月末按目标月份最后一天截断；“上个月”表示上一个完整自然月。记录实际起止日期、时区、包含边界和取数时间，不用宿主机日期覆盖会话提供的用户日期。不要因近期无提交而悄悄改用最近一条提交的月份。
- 记录分支、目标 SHA、浅克隆状态及工作区状态。默认只分析已提交内容；有未提交修改时，读取固定目标版本，避免混入正在开发的功能。
- 已知生产部署 SHA 或镜像对应 SHA 时，以它限定“已上线”。仅有“公司部署了该项目”不足以推断当前 HEAD 已上线；无需因此阻塞代码清单，标注“已合入，线上待核实”。不读取部署凭据，也不因生成公告而触发 Docker 发布或 1Panel 部署。

## 收集及交叉核实

按以下思路选择 Git 命令，参数替换为已解析的实际值：

```text
git branch --show-current
git rev-parse HEAD
git rev-parse --is-shallow-repository
git status --short
git log TARGET --since-as-filter=START --until=END --format="%H %cI %s"
git log TARGET --first-parent --format="%H %cI %s"
git log BASE..TARGET --no-merges --format="%H %cI %s"
git diff --name-status BASE TARGET
git diff BASE TARGET -- relevant/path
git show TARGET:relevant/path
```

- 日期边界使用带时区的时间；有明确版本范围时，以版本差异为准，日期只是辅助。按日期分析时，选择窗口开始前的主线提交作为 BASE、窗口结束前的最后一个主线提交作为 TARGET，并确认祖先关系；当前未结束的窗口以取数时的目标提交为截止。提交时间乱序或缺少历史时说明范围限制，不伪造完整覆盖。
- 主线日志用于确认何时合入；同时检查 `BASE..TARGET` 的完整可达历史，包含合并带入的上游提交，不能仅用 `--first-parent`、作者、`feat` 前缀或提交日期筛选功能。旧日期提交在本期首次合入也可能属于本期；窗口内提交但基线已包含的内容不算新增。
- 读取目标版本的 `changes/CHANGELOG.md` 及相关详情作为线索；该文件只记录本地二开，且同一条目会累积多个月、多个功能的变化，不能直接把日期命中的整条内容当作本月新增。公告可包含本期实际采用的上游功能，无需将它们补写进二开日志。
- 每项入选更新至少核对提交差异与目标版本中的入口/实现；对照 BASE 判断新增、优化、修复或行为调整。合并提交的标题不是功能证据，已回退、被后续覆盖或本地未采用的实现不得作为已交付功能。
- 特别注意本地已有能力：上游新增某项账号或登录能力，而本地早已有同等实现且最终仍保留旧行为时，不应宣传为公司本月首次获得该功能。
- 以目标版本实际代码为准：当前唯一前端是 `web`，从 `web/src/App.tsx`、页面和菜单确认入口及可见条件，再按需检查 `controllers/`、`object/`、`routers/` 等实现。不要从已移除的 `web-old`、上游截图或文档推断当前界面。
- 本地已移除的商业订阅限制、积分/排名、Casdoor Cloud 推广、旧 AI 助手及 Web3 登录等内容不能因上游仍有实现就宣传为可用；移除行为本身也只有在本期净差异中才计入。
- 仅做公告事实整理，不自动扩展成安全审计或业务修改。不读取真实账号资料、密码、密钥或令牌作为公告示例。

## 筛选与措辞

- 优先保留员工实际能感知的登录、密码找回、账号安全、个人资料、应用入口、页面交互及稳定性变化；同一功能的多次提交合并成一个条目。
- 用“在什么场景下，现在可以怎样做”描述效果，不逐条翻译 commit，不堆框架名、字段名、代码重构或依赖版本。没有测量证据不写速度提升百分比、节约金额或“彻底解决”。
- 区分普通员工、组织管理员、系统管理员与应用接入人员。用户列表、组织配置、字段权限、登录记录和应用配置等能力需核对实际授权，不能因存在页面路由就写成全员可用。
- 区分“新增能力”和“改进已有功能”：资料展示改进不等于员工获得编辑权限，用户搜索优化不等于开放全公司通讯录，登录提供商或认证协议支持不等于公司已经启用该登录方式或接入所有业务系统。
- 标注组织、应用、角色、字段读写权限、登录方式及管理员配置等生效条件。多因素认证、单点登录、LDAP/外部身份源同步等是否已启用未知时，放入条件项，不混进已上线主清单；不能把资料同步写成允许手动修改外部身份源字段。
- 员工需要知道的变化不能漏掉，例如登录入口迁移、登录方式移除、会话失效需重新登录、资料必填或校验规则调整。只写本期有证据的行为变化；应用接入参数、协议兼容调整和管理员操作要求放入对应补充区。
- 纯格式化、内部工具/技能维护、测试调整、无可见效果的依赖升级不单列公告。后台清理与界面标识移除按实际用户价值决定是否入选，不把提交数等同于功能数。

## 交付

生成两份内容，用户指定格式或位置时优先遵循；需要落盘且未指定位置时，保存到仓库 `changes/announcements/`，以日期范围命名，例如 `YYYY-MM-DD_to_YYYY-MM-DD-features.md` 与 `YYYY-MM-DD_to_YYYY-MM-DD-announcement.md`。已有文件不覆盖用户编辑，除非用户要求更新该文件。不要改写二开 `changes/CHANGELOG.md`，不要在 `docs/` 或技能目录生成公告。

1. **功能更新清单**：开头列统计范围、BASE/TARGET、代码与生产的确认状态；按读者归类。每项包括变化类型、用户价值、使用入口、适用条件及代表提交/目标代码路径。附简短的排除说明、待核实事项与实际执行的取数/检查命令。没有运行验证就不要复制旧文档的“构建通过”作为本次结果。
2. **公司公告草稿**：保留中文标题，正文直接以功能亮点的有序列表开始，不写称呼或开场引言；每项提供可操作入口，不出现 SHA、代码路径、管理员专属指标或技术维护清单。通常控制在 500～900 字，按实质变化调整。必要的使用变化单独提醒。发布状态未知时明确标注草稿及待部署核实，不虚构上线时间、公司链接或联系人。

### 公司公告草稿格式

- 页面、功能和入口名称直接写出，不使用直角引号或装饰性括号包裹。
- 功能亮点使用真正的 Markdown 有序列表，按 `1.`、`2.`、`3.` 依次编号；序号放在加粗标记外，例如 `1. **个人资料展示优化**`，不要写成 `**1. 个人资料展示优化**`。
- 每个有序列表项下的说明拆成无序列表，使用 `-`，统一缩进四个空格。每点说明一个变化、入口、条件或使用提醒，不在编号下面堆放未分点的段落。
- 有序列表标题可以加粗，但其下无序列表的分点内容不使用加粗，包括“使用提醒”等提示标签。
- 公告列表内部不留空行：有序列表项之间、有序标题与其无序子列表之间、无序子列表项之间均连续换行。保留 Markdown 标记后的必要空格及子列表的四空格缩进。
- 不写“各位同事”或“本期更新主要围绕”等开场文字。标题和草稿状态提示之后直接进入有序列表。
- 结尾说明独立于列表，与最后一个列表项之间保留一个空行，并将整段结尾加粗；结尾不缩进。
- 文档中不附加“编辑备注”“正式发送时删除”、条目删改建议或发送状态等内部编辑说明，也不将这些备注搬到其他交付文档。公告在加粗结尾处结束，不追加分隔线或备注区；如有必要的编辑沟通，仅在对话中简短说明。功能清单仍保留事实核实所需的待核实事项。

以下仅演示排版，功能和入口必须按本期证据替换，不是已交付功能声明：

```markdown
# 统一身份平台功能更新

草稿：以下变化已合入代码，线上部署状态待核实。

1. **个人资料展示优化**
    - 在个人账号页面查看更清晰的资料信息。
    - 可查看和修改的字段以所在组织的配置为准。
2. **应用访问更方便**
    - 在应用列表中查找并进入已授权的业务应用。
    - 可见应用以账号权限和公司实际接入情况为准。

**各功能的可见范围以账号权限和公司实际配置为准。请通过原有统一身份平台入口访问。**
```

交付前核对每个公告亮点能回溯到清单，生效条件没有丢失，移除/回退内容未被宣传，已有功能未重复当作新增，并检查上述公告格式。没有实质用户变化时如实说明，不凑满条数。

生成清单或草稿不意味着获准群发；仅在用户明确要求发送并确定渠道、接收范围后使用对应服务工具。

## 调用示例

- `/announce`：整理当前 HEAD 最近一个月的功能更新与公司公告草稿。
- `/announce 上个月`：按用户时区的上一个完整自然月整理更新。
- `/announce 从 <旧版本> 到 <新版本>`：核对两个版本之间的实际变化并生成清单与草稿。
- “整理 Casdoor 近期上线公告，面向全体员工”：生成员工可读的草稿；上线状态以可核实的部署版本为准。
