# 上游合并规则（二开 Fork 项目）

本项目是深度二开 fork。**优先保护本地功能，逐文件审查，常规问题自主处理，集中汇报结果。**

## 核心原则

1. **保护二开**：不得静默覆盖或删除本地功能。双方可兼容时优先手动合并；无法兼容时优先保留本地，并记录未接入的上游内容。
2. **先审查再执行**：核实调用方、类型、配置、依赖及 CHANGELOG，逐文件给出唯一推荐并直接执行，不逐项等待用户确认。
3. **禁止盲目批量解决**：不得用 `git merge -X ours/theirs`、批量 checkout 或批量 accept incoming 跳过审查。
4. **可回滚**：在独立合并分支操作，使用 `--no-commit --no-ff` 留出审查窗口，不直接在目标分支合并上游。

## 执行与确认边界

本节是整个流程唯一的确认标准，适用于预览、冲突解决、自动合并审查及文件新增、删除。

**默认连续执行**：在已授权范围内完成调查、编辑、`git add` 和验证。冲突数量、文件数量、CHANGELOG 关联、手动编辑、重点目录及普通兼容调整均不触发确认；审查与汇报不等于请求批准。

用户要求合并上游后，常规冲突解决即在授权范围内：逐文件审查后直接执行推荐方案，不询问“是否采用此方案”“是否暂存”或“是否继续”。只有下列五类情况中尚未授权的具体方案需要用户手动确认，不得自行增加确认条件。

**不得分段停下等待“继续”**：处理完一个文件、一组冲突或一个功能模块后，通过进度消息汇报并继续执行，不得以阶段性最终回复结束回合。冲突多、工作量大、调用链尚待调查、审查或验证尚未完成，均不是等待用户确认的理由。应持续完成全部常规冲突解决、自动合并审查及可执行验证；遇到确实无法自行排除的执行阻塞时，如实说明证据和恢复条件，不得将其包装为方案确认。

**仅以下情况需要确认尚未授权的具体方案**：

1. 跨模块复杂重构：多个模块耦合调整，涉及难以可靠判断的行为兼容或实现取舍；普通跨文件适配不属于此类。
2. 核心登录/权限流程大幅改写。
3. 破坏性数据库迁移。
4. 重要接口不兼容。
5. 新增重大风险，或操作超出已授权范围。

已有授权持续有效；已确认的范围和方案直接执行，仅针对新增重大风险或超出授权的部分再次确认。提交、推送及远端分支删除沿用当前会话授权，本技能不自动授予这些权限。

证据不足时先继续调查，不得编造兼容结论，也不得仅以“尚不确定”要求用户逐项判断。若调查后发现上述情形，先完成可独立进行的工作，再用 AskQuestion 集中确认同一决策涉及的文件：说明触发条件、具体行为影响、推荐方案、关键代码或差异及回滚办法。仅暂停依赖该决定的操作，其他工作继续。

## 逐文件说明格式

冲突文件及双方都修改过的自动合并文件，逐一记录：

1. **当前本地逻辑**：合并前的行为、二开不变量及对应 CHANGELOG 编号，不得与暂存结果混淆。
2. **上游修改逻辑**：相对共同基线的改动、解决的问题及跨文件依赖。
3. **方案与结论**：简述保留本地、采用上游、手动合并各自保留和损失的内容；不适用的方案注明原因。给出唯一推荐、依据和执行结果。

常规文件可按功能分批汇报，每个文件仍须有记录，无需逐个展示完整 diff 或等待回复。需要确认时再展开关键差异和可行选项，选项须说明实际结果、风险，并仅标记一个【最终推荐】。

## 合并流程

### 第 1 步：准备（在合并前执行）

```bash
# 确保工作区干净
git status  # 必须无未提交的修改

# 确认 upstream remote 存在，不存在则添加
git remote -v
# 若无 upstream：git remote add upstream <上游仓库URL>

# 拉取上游最新代码（仅 fetch，不合并）
git fetch upstream

# 从已核实的目标分支创建，默认目标为 v1
git switch v1
git checkout -b merge/upstream-YYYY-MM-DD
```

### 第 2 步：预览上游变更（合并前必看，决定是否继续）

记录合并前本地提交 `<local-before>`、本次上游提交 `<upstream-tip>` 及共同基线。后续使用固定提交核对，避免远端引用移动影响审查。

```bash
# 查看上游领先本地多少个 commit
git log HEAD..upstream/main --oneline -30

# 查看上游变更了哪些文件及变更量
git diff HEAD...upstream/main --stat

# 列出变更路径，核对二开记录
git diff HEAD...upstream/main --name-status
```

#### 2.1 交叉比对二开变更日志

读取 `changes/CHANGELOG.md`（及 `changes/details/` 目录下的详情文件），提取所有二开修改过的文件列表。将上游变更文件与该列表交叉比对，标出哪些二开功能会受上游更新影响：

- **二开关联文件**：逐一核实功能和依赖，即使自动合并成功也要详细审查。
- **其余文件**：结合本地历史和调用关系判断影响，不能仅因未记入 CHANGELOG 就认定安全。

按功能展示影响摘要，列出 CHANGELOG 编号、关联路径及待核实风险，然后直接继续。可分批审查和汇报，但不能拆散必须一起处理的跨文件契约。

### 第 3 步：执行合并（保留冲突标记，随后逐文件审查处理）

```bash
# 合并但不自动提交，冲突保留标记供逐文件审查
git merge upstream/main --no-commit --no-ff
```

- `--no-commit`：合并后不自动提交，留出审查窗口。
- **不使用** `-X ours` 或 `-X theirs`：冲突以标记形式保留，确保逐文件审查后再执行推荐方案。
- 上游的**新增文件**会被正常引入（无冲突），仍需审查。

### 第 4 步：分类所有变更文件

合并后先建立全局视图，将文件分为四类分别处理：

```bash
# 列出冲突文件（未合并状态）
git diff --name-only --diff-filter=U

# 列出已自动合并的变更文件（已暂存）
git diff --cached --name-status

# 列出上游新增的文件
git diff --cached --name-status --diff-filter=A
```

按以下优先级呈现给用户：

1. **冲突文件**（`U` 状态）→ 必须逐一走完冲突解决流程（第 5 步）
2. **已自动合并的修改文件**（`M` 状态）→ 审查 diff，按确认边界执行推荐方案
3. **上游新增文件**（`A` 状态）→ 审查内容及依赖，按确认边界决定是否保留
4. **上游删除的文件**（`D` 状态）→ 核实本地功能影响，按确认边界决定是否跟随删除

### 第 5 步：逐文件解决冲突

每个冲突文件依次完成，不能跳过审查：

1. 查看 `git diff -- <file>`，读取完整文件及必要的基线、本地、上游版本，核实关联调用和 CHANGELOG。
2. 按“逐文件说明格式”记录对比及唯一推荐。双方可兼容则手动合并；上游破坏二开且无法兼容则保留本地；仅在本地功能经核实完整保留时采用上游。
3. 常规方案直接编辑并执行 `git add -- <file>`。单文件采用 ours/theirs 前必须核实整份文件，防止丢掉冲突区域以外的改动。
4. 检查该文件已退出冲突列表，记录保留的本地逻辑、接入及未接入的上游逻辑和执行依据。

重复直到 `git diff --name-only --diff-filter=U` 为空。需要确认的文件按统一边界处理，保持未解决状态，不阻塞无依赖的文件。

### 第 6 步：审查已自动合并的文件

**自动合并成功不代表行为正确。** 审查所有暂存变更：

- 仅上游修改、本地无改动的文件：可按功能批量审查 diff 和依赖，汇总结果。
- 双方都修改过、CHANGELOG 关联或位于本地独有目录的文件：逐一审查 diff，按“逐文件说明格式”记录，核实本地功能和跨文件契约。

每个文件选择接受自动合并、恢复合并前版本或手动调整，说明依据后直接执行。恢复前须核实是否会遗漏必要的上游依赖。

### 第 7 步：审查上游新增与删除的文件

- **新增文件**：逐一记录路径、用途和依赖，核实后接入；与本地独有路径冲突时提示用户并优先保护本地内容。
- **删除文件**：核实调用方、替代实现及二开影响；有本地修改时优先保留，能证明替代实现完整保留功能时可跟随删除。

常规方案直接执行，确认条件仅引用“执行与确认边界”。

## 本地独有目录保护

以下目录/文件是本地独有的，上游仓库中不存在。合并时若上游新增了同名路径，**必须立即警告用户并默认保留本地版本**：

- `changes/` — 二开变更日志
- `.cursor/` — Cursor IDE 配置与规则
- `.agents/` — Agent 技能与配置

## 合并后验证（第 8 步，不可跳过）

提交前完成以下验证；提交后核对最终提交内容。未获提交授权时也应先完成可执行的验证。

### 8.1 编译验证

```bash
go build ./...
```

构建失败时先区分合并遗漏、上游问题和环境问题；代码问题修复后重新验证，环境阻塞如实记录。涉及前端或依赖变更时，执行相应构建和必要检查。不得未经要求新增 Go 测试。

### 8.2 逐提交文件对比

对本次合并范围内的每个上游提交，逐一检查其涉及的文件是否在本地正确体现：

```bash
# 列出本次合并包含的所有上游提交
git log <local-before>..<upstream-tip> --oneline --no-merges

# 对每个上游提交，获取涉及的文件列表
git show <commit-hash> --stat --name-only

# 对比每个文件的当前状态与上游
git diff <upstream-tip> -- <file-path>
```

### 8.3 分类差异

无差异表示对应文件已接入；有差异则结合 CHANGELOG、合并前代码和调用关系逐项解释。已记录的二开差异也须验证保留正确；未记录的差异须查证，不能直接认定为遗漏或合理定制。无合理依据的上游逻辑缺失或新增文件缺失必须修复。

### 8.4 跨文件检查

- 函数签名、类型和字段变更必须同步所有调用及引用。
- 新增定义与调用必须同时接入，不能因单文件保留本地而遗漏上游必要重构。
- 旧实现被替代时核实入口、任务调度和调用链，避免新旧实现重复运行。
- 核实新增文件、依赖声明及锁文件，拆开审查同一文件中的品牌定制和功能改动。
- 遵守项目明确不迁移的功能和只读目录规则，不恢复已主动移除的功能。

## 合并后复盘与上线交接（第 9 步，不可跳过）

合并提交创建并完成第 8 步验证后，必须完整读取并执行 `../upstream-merge-review/SKILL.md`，生成合并后复盘报告。若用户尚未授权创建合并提交，则保持当前安全停点，不得把暂存结果描述为最终合并结果。

报告覆盖上游变更、实际接入内容、二开影响、上线变化、人工测试及自动验证，具体交付要求见“最终输出”。

复盘必须基于 merge commit 的两个父提交、共同基线、最终代码和 `changes/CHANGELOG.md`，不得只复述上游 commit message。报告默认只读，不得为上游同步或冲突解决新增二开 CHANGELOG 条目。

## 合并分支清理（第 10 步，不可跳过）

合并完成并将目标分支 `v1` 成功推送到 `origin/v1` 后，必须删除本次使用的旧合并分支，避免长期残留 `merge/upstream-*` 分支。

删除前必须同时确认：

1. 当前 `v1` 与 `origin/v1` 指向同一提交；
2. 本地合并分支的 tip 已包含在 `v1`；
3. 若存在同名远端分支，其 tip 已包含在 `origin/v1`；
4. 当前不在待删除的合并分支上。

```bash
# 比较以下两条命令的结果，必须一致
git rev-parse v1
git rev-parse origin/v1

# 确认本地与远端合并分支均已进入目标分支
git merge-base --is-ancestor merge/upstream-YYYY-MM-DD v1
git merge-base --is-ancestor origin/merge/upstream-YYYY-MM-DD origin/v1

# 先删除远端分支（若存在），再安全删除本地分支
git push origin --delete merge/upstream-YYYY-MM-DD
git branch -d merge/upstream-YYYY-MM-DD
```

- 只能使用 `git branch -d` 安全删除；如果 Git 判断分支尚未合并，禁止改用 `-D` 强制删除，必须先查明遗漏提交。
- 若同名远端分支不存在，可跳过远端删除，但仍须删除本地合并分支。
- 删除后使用 `git branch --list` 和 `git branch -r --list` 确认本地、远端引用均已消失，并在最终交付中记录清理结果。
- 尚未完成合并提交、复盘验证或 `v1` 推送时，不得提前删除合并分支。

## 最终输出与处理详情（每次交付必需）

最终回复先给当前结论和关键行为变化，再提供以下详情；没有的事项写“无”或“不适用”：

1. **状态与范围**：来源、目标、提交标识、当前分支、剩余冲突，以及提交、推送、分支清理状态。
2. **实际接入内容**：按功能说明修复、新能力和结构调整，以及用户可观察的 UI、接口、配置变化，链接关键文件。
3. **二开功能状态**：受影响的 CHANGELOG 编号、保留或兼容调整结果、待处理项及代码或验证依据。
4. **决策与未接入内容**：逐一记录冲突及双方修改文件的方案、理由、保留和舍弃的逻辑、具体影响；标明直接执行或用户确认，说明重要新增、删除文件的处理。
5. **验证与限制**：列出构建、检查、测试的实际结果，区分通过、失败、未执行和受阻。编译通过不代表业务验证通过。
6. **上线与人工验证**：配置、依赖、数据库、部署要求；关键人工测试的前置条件、步骤、预期结果和失败判定。
7. **剩余事项**：阻塞、待确认决策、待执行验证及尚未授权的操作，给出明确下一步。

已提交时结合第 9 步复盘；未提交时基于合并前版本、固定上游提交和工作区说明阶段结果。长篇逐文件记录可链接报告，正文仍须保留关键取舍、未接入内容、验证限制和待办，不得仅给文件数量或报告链接。

## 异常与回滚

- 上游声明 breaking change 时先核实本项目的实际影响，仍按统一确认边界处理。
- 有未解决问题时说明证据、影响和安全停点，不把暂存结果描述为已完成合并。
- 用户要求放弃未提交的合并时，使用 `git merge --abort`；核实工作区后切回原目标分支。不得强制删分支或丢弃用户修改。
