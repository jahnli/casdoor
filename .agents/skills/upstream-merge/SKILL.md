# 上游合并规则（二开 Fork 项目）

## 原则

1. **保护二开**：不得静默覆盖或删除本地功能。双方可兼容则手工合并；不可兼容则保留本地，并记录未接入的上游内容。
2. **先审查再执行**：核实调用方、类型、配置、依赖及 `changes/CHANGELOG.md`，逐文件给出唯一推荐后直接执行。
3. **禁止批量选边**：不得用 `-X ours/theirs`、批量 checkout、批量 accept incoming 跳过审查。
4. **可回滚**：只在 `merge/upstream-YYYY-MM-DD` 分支操作，用 `--no-commit --no-ff` 留审查窗口。

## 执行纪律

用户要求合并即已授权冲突解决：冲突文件的三方案对比与最终推荐由你**自主完成并按推荐直接执行**，不询问"是否采用此方案""是否暂存""是否继续"，也不要把"我建议 X，是否同意"抛回用户。唯一例外是下文五类尚未授权的方案。

每批按 **调查 → 决策记录 → 编辑暂存 → 验证更新** 推进，进度消息发出后继续调用工具。

- **不是停下理由**：冲突数量、文件数量、CHANGELOG 关联、手动编辑、重点目录、普通兼容调整、调用链待查、尚未验证、耗时、上下文不足。审查与汇报不等于请求批准。
- **冲突列表清空后**仍须继续第 6 步审查、第 8 步验证及已授权的后续操作。
- **证据不足先调查**，不得编造兼容结论，也不得以"尚不确定"要求用户逐项判断。

只有下列**尚未授权的具体方案**才需用 AskQuestion 集中确认（同一决策涉及的文件成组提问，写明触发条件、行为影响、推荐方案、回滚办法），期间其他独立工作继续：

1. 跨模块复杂重构：多模块耦合、行为兼容难以可靠判断（普通跨文件适配不算）。
2. 核心登录/权限流程大幅改写。
3. 破坏性数据库迁移。
4. 重要接口不兼容。
5. 新增重大风险，或操作超出已授权范围。

判断依据是方案的行为变化，不是文件所在目录或冲突类型。已确认的范围继续有效；提交、推送及远端分支删除沿用当前会话授权，本技能不自动授予。

**仅以下情况可以结束回合**：

- 授权范围内工作全部完成；未授权提交时先完成第 5～8 步，交付未提交的审查结果。
- 剩余工作全部依赖上述待确认决策，且其他独立工作已完成。
- 确实无法自行排除的执行阻塞，且其他可执行工作已完成（说明失败操作、实际错误、已尝试处理、恢复条件）。
- 用户明确要求暂停、取消或改变任务。

## 进度记录与续接

长任务开始时建立记录，每批后更新。路径优先 `git rev-parse --git-path upstream-merge-progress.md`，已存在则先读、不覆盖其他任务记录；不得写入业务提交或二开 CHANGELOG。

```markdown
# upstream-merge 进度 · merge/upstream-2026-11-01

- 固定提交：local-before=3f1c9ab / upstream-tip=8d2e0f4 / merge-base=5a77021
- 已确认决策：无（五类均未触发）
- 已完成：object/user.go【已暂存】、controllers/auth.go【已编辑】
- 待处理：object/syncer_user.go（冲突）、web/src/pages/（自动合并待审）
- 验证：go build ./... 未执行
- 下一项：解决 object/syncer_user.go
```

- 上下文接近上限时先更新记录；环境提供压缩能力则自动调用（不编造压缩工具，也不声称已执行未发生的压缩）。压缩后读记录，核对分支、`HEAD`、`MERGE_HEAD`、工作区和冲突列表，从首个未完成事项继续，不重新询问"是否继续"。
- 状态未变的审查无需重做，受后续编辑影响的结论须复核；状态与记录不符先查差异，保护用户新增修改。
- 不因压缩重新 fetch、更换固定上游提交、重建分支、重复 merge 或丢弃已处理结果；执行能力真正耗尽时按阻塞报告记录位置与恢复步骤。

## 逐文件说明格式

冲突文件及双方都改过的自动合并文件，逐个记录三项。这套对比是你自己得出推荐的过程，**不是向用户征询选项**；推荐即执行方案，写完立即动手。**给推荐前必须核实调用方、类型、配置、依赖及 CHANGELOG 关联**，未核实不得先给结论。

1. **当前本地逻辑**：合并前本地版本怎样运行、提供什么二开功能、对应哪个 CHANGELOG 条目或本地不变量。"当前"固定指合并前的本地版本，不得与 Git 自动合并后的暂存结果混淆。
2. **上游修改逻辑**：`<upstream-tip>` 相对共同基线新增、删除或重构了什么，解决什么问题，引入什么跨文件契约。
3. **最终推荐**：先分别说明各方案选后的实际运行逻辑和损失，再收口到唯一推荐。**双方可兼容时必须走手动合并**，不得为了省事直接选边。
   - **保留本地**：最终文件怎样运行，会缺少哪些上游修复、功能或结构性改动。
   - **采用上游**：最终文件怎样运行，会丢失哪些本地功能、破坏哪些二开不变量。
   - **手动合并**：仅在双方可兼容时说明合并后的运行逻辑；不适用时写明原因。
   - **推荐**：只选一个，用一两句说明为何它同时满足本地功能保护、上游改动接入、编译与跨文件契约。

推荐后的逻辑属于第 3 项，不另起第四段。解决完成后在同一条目末尾补 `已执行：…` 记录实际结果。

```markdown
**object/syncer_user.go**（冲突，关联 001）

1. 本地：`getCasdoorColumns()` 用 `isRemovedUserMetric()` 过滤 score/karma/ranking；
   `initAdapter()` 对仍引用旧字段的同步器报错拒绝连库。二者是 001 的不变量。
2. 上游：`calculateHash()` 增加同步列的二次校验，直接引用 `user.Score`；
   同时去掉 `getCasdoorColumns()` 的过滤条件——上游没有"已移除字段"的概念。
3. 最终推荐：
   - 保本地：不会把已删除字段写回，但拿不到上游的取值校验，之后上游再改
     `calculateHash()` 会反复冲突。
   - 采上游：编译失败——`User.Score` 字段已在 001 中删除。
   - 手工合并：接上游二次校验，保留 `isRemovedUserMetric` 守卫，两者正交。
   - **推荐**：手工合并。守卫是 001 的不变量必须保留；二次校验不改字段集合，
     合并后既通过编译又完整接入上游改动。

已执行：手工合并，`go build ./...` 通过。
```

常规文件可按功能分批汇报，但每个文件仍须有记录，不必逐个展示 diff。确实落入五类确认事项时，再展开关键差异、写明推荐与回滚办法并提问；其余一律直接执行。

## 合并流程

### 第 1 步：准备

先核实仓库路径、当前分支和合并状态。已有本次未完成合并时，读进度记录、核实 `MERGE_HEAD` 与固定提交后从第 4 步恢复（合并产生的改动不算"工作区不干净"）；合并已结束时按记录与 Git 历史确定下一步，不重复发起。

```bash
git status                                       # 必须无未提交修改
git remote -v                                    # 无 upstream 则 git remote add upstream <URL>
git fetch upstream
git switch v1 && git checkout -b merge/upstream-YYYY-MM-DD
```

### 第 2 步：预览上游变更

核实上游实际默认分支或用户指定来源，不假定是 `main`。固定 `<local-before>`、`<upstream-tip>` 及共同基线，后续都用固定提交 ID 核对，避免远端引用移动。

```bash
git log <local-before>..<upstream-tip> --oneline -30
git diff <local-before>...<upstream-tip> --stat
git diff <local-before>...<upstream-tip> --name-status
```

读 `changes/CHANGELOG.md`（含 `changes/details/`），提取二开改动过的文件与上游变更交叉比对。**二开关联文件**（自动合并成功也要详细审查）；**其余文件**结合本地历史和调用关系判断，不能仅因未记入 CHANGELOG 就认定安全。

按功能给出影响摘要后直接继续，可分批汇报但不能拆散必须一起处理的跨文件契约：

| 编号 | 关联路径                                  | 上游改动                        | 风险                      |
| ---- | ----------------------------------------- | ------------------------------- | ------------------------- |
| 001  | `object/syncer_user.go`                   | 同步映射重构，重新加入 score 列 | 高：本地已删除该字段      |
| 002  | `web/src/components/layout/AppLayout.tsx` | 页脚组件重写                    | 中：本地已去掉 Powered by |

### 第 3 步：执行合并

```bash
git merge <upstream-tip> --no-commit --no-ff
```

冲突保留标记。上游新增文件会被直接引入，但仍需审查。merge 因冲突返回非零退出码是本流程正常分支：确认 `MERGE_HEAD` 存在后进入第 4、5 步，不当作工具阻塞；其他错误按实际输出调查。

### 第 4 步：分类变更文件

```bash
git diff --name-only --diff-filter=U              # 冲突（未合并）
git diff --cached --name-status                   # 已自动合并
git diff --cached --name-status --diff-filter=A   # 上游新增
```

优先级：`U`（第 5 步）→ `M`／`A`／`D`（第 6 步）。

### 第 5 步：逐文件解决冲突

对每个冲突文件：读完整文件及必要的基线／本地／上游版本，核实关联调用和 CHANGELOG → **先做完三方案对比，再给唯一推荐** → 编辑后 `git add -- <file>` → 确认退出冲突列表。

对比必须先于动手：不得先改代码再回填理由，也不得只写"保留本地更稳"这类无依据结论。每个方案都要落到具体后果——编译是否通过、哪项二开功能消失、哪些上游修复拿不到。单文件采用 ours/theirs 前必须核实整份文件，防止丢掉冲突区域以外的改动。

解决：保留本地的 `isRemovedUserMetric` 守卫，同时接入上游在同一循环内新增的其他处理；结论记为"上游去掉旧字段过滤，按 001 保留守卫"。反向情况——上游删除、本地保留——只有在本地功能被上游替代实现完整覆盖时才跟随删除。

重复直到 `git diff --name-only --diff-filter=U` 为空。需确认的文件按确认边界处理并保持未解决，不阻塞无依赖的文件。

### 第 6 步：审查自动合并、新增与删除的文件

**自动合并成功不代表行为正确。**

- 仅上游修改、本地无改动：可按功能批量审查 diff 与依赖并汇总。
- 双方都改过、CHANGELOG 关联、本地独有目录：逐一审查，按格式记录，核实本地功能与跨文件契约。
- **新增文件**：记录路径、用途和依赖，核实后接入；与本地独有路径冲突时警告用户并保留本地内容。
- **删除文件**：核实调用方、替代实现及二开影响；本地有修改时优先保留，能证明替代实现完整保留功能时才跟随删除。

每个文件选择接受自动合并／恢复合并前版本／手动调整并说明依据后直接执行；恢复前核实是否会遗漏必要的上游依赖。

### 第 7 步：本地独有目录保护

以下路径上游不存在。若上游新增同名路径，**必须立即警告用户并默认保留本地版本**：`changes/`（二开变更日志）、`.cursor/`（IDE 配置与规则）、`.agents/`（Agent 技能与配置）。

### 第 8 步：验证（不可跳过）

**8.1 编译**：`go build ./...`。失败先区分合并遗漏／上游问题／环境问题，修好后重跑；涉及前端或依赖变更时执行相应构建和检查。不得未经要求新增 Go 测试。

**8.2 逐提交比对**：

```bash
git log <local-before>..<upstream-tip> --oneline --no-merges
git show <commit-hash> --stat --name-only
git diff <upstream-tip> -- <file-path>
```

**8.3 差异分类**：无差异即已接入；有差异须结合 CHANGELOG、合并前代码与调用关系逐项解释。已记录的二开差异验证保留正确，未记录的差异查证而非默认判为遗漏或合理定制；无依据的上游逻辑或新增文件缺失必须修复。

**8.4 跨文件检查**：

- 函数签名、类型、字段变更同步所有调用与引用。
- 新增定义与调用必须同时接入，不能因单文件保留本地而漏掉上游必要重构。
- 旧实现被替代时核实入口、任务调度和调用链，避免新旧实现重复运行。
- 核实新增文件、依赖声明及锁文件；同一文件中的品牌定制与功能改动拆开审查。
- 遵守不迁移功能（AI assistant、Web3）的约定，不恢复已删除的旧前端目录（`web-old/`）或已主动移除的功能。

### 第 9 步：复盘与上线交接（不可跳过）

合并提交创建并通过第 8 步验证后，必须读取并执行 `../upstream-merge-review/SKILL.md` 生成复盘报告。未授权提交时先完成第 5～8 步再停在待提交状态，不得以"未授权提交"为由跳过冲突解决、审查或验证，也不得把暂存结果说成最终合并结果。

复盘依据 merge commit 与共同基线核对最终代码，不得只复述上游 commit message；报告只读，不为上游同步新增二开 CHANGELOG 条目。

### 第 10 步：分支及合并记录清理（不可跳过）

`v1` 成功推送到 `origin/v1` 后才可删除本次合并分支，删除前四项须同时成立：`v1` 与 `origin/v1` 为同一提交；本地合并分支 tip 已包含在 `v1`；同名远端分支 tip 已包含在 `origin/v1`；当前不在待删分支上。

```bash
git rev-parse v1 && git rev-parse origin/v1
git merge-base --is-ancestor merge/upstream-YYYY-MM-DD v1
git merge-base --is-ancestor origin/merge/upstream-YYYY-MM-DD origin/v1
git push origin --delete merge/upstream-YYYY-MM-DD   # 远端不存在则跳过
git branch -d merge/upstream-YYYY-MM-DD
```

只能用 `git branch -d`；Git 判断未合并时禁止改用 `-D`，先查明遗漏提交。删除后用 `git branch --list` 和 `git branch -r --list` 确认引用消失，并在交付中记录清理结果。

分支清理完成后，核对本次合并创建的进度、冲突决策等临时 Markdown 记录，并清理属于本次合并的记录；记录混有其他任务内容时，只删除本次合并部分，保留其他内容。不得删除业务文档、二开 CHANGELOG 或其他任务的记录。清理前确认复盘和交付所需信息已保存；在交付中说明已清理或保留的记录及原因。`v1` 尚未成功推送或分支清理条件未满足时，保留这些记录供续接。

## 交付格式

先给结论和关键行为变化，再列（无则写"无"或"不适用"）：

1. **状态与范围**：来源、目标、提交标识、当前分支、剩余冲突，提交／推送／分支清理状态。
2. **实际接入内容**：按功能说明修复、新能力和结构调整，接口与配置变化，链接关键文件。
3. **UI 变化**：单独归纳用户可见的界面与交互变化，包括页面入口、布局、组件、文案、状态反馈、响应式行为和操作流程。说明变更前后差异、影响的角色或使用场景，以及最终界面采用上游实现、本地实现还是兼容适配；仅内部重构、测试调整或无可见效果的前端改动不得列为 UI 变化。若本次没有 UI 变化，明确写明"无用户可见的 UI 变化"。措辞与 `upstream-merge-review` 的 UI 项保持同步。
4. **二开功能状态**：受影响 CHANGELOG 编号、保留或兼容调整结果、待处理项、代码或验证依据。
5. **决策与未接入内容**：冲突及双方修改文件的方案、理由、保留与舍弃的逻辑、具体影响；标注直接执行或用户确认；重要新增／删除文件的处理。
6. **验证与限制**：构建、检查、测试的实际结果，区分通过／失败／未执行／受阻。编译通过不等于业务验证通过。
7. **上线与人工验证**：配置、依赖、数据库、部署要求；关键人工测试的前置条件、步骤、预期结果、失败判定。
8. **剩余事项**：阻塞、待确认决策、待执行验证、未授权操作及明确下一步。

```markdown
3. UI 变化：001 移除用户编辑页、组织编辑页的信誉分/积分/排名输入项，用户列表不再显示这三列；
   002 的页脚保持本地实现，登录页与后台不渲染 Powered by，页脚 HTML 为空时整块页脚不占位。
4. 二开功能状态：001 保留——上游再次引入 score 列，已在 `object/syncer_user.go` 拒绝；
   `web/src/pages/` 只接入上游的分页重构。依据：`go build ./...` 通过，`rg "Score" object/` 无残留。
```

已提交时结合第 9 步复盘；未提交时基于合并前版本、固定上游提交和工作区说明阶段结果。长篇记录可链接报告，正文仍须保留关键取舍、未接入内容、验证限制和待办。

## 异常与回滚

- 上游声明 breaking change 时先核实本项目实际影响，仍按确认边界处理。
- 用户要求放弃未提交的合并时用 `git merge --abort`，核实工作区后切回原目标分支。不得强制删分支或丢弃用户修改。
