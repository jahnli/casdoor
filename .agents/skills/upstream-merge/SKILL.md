# 上游合并规则（二开 Fork 项目）

本项目是上游仓库的深度二开 fork，已有大量本地修改。合并上游更新时必须极其谨慎，**本地改动优先，绝不允许丢失本地功能**。

## 核心原则

1. **本地功能保护**：不得丢失或静默覆盖二开功能。若双方改动可以兼容，应优先评估手动合并；只有在改动互斥且无法证明上游方案完整保留本地功能时，才推荐保留本地。
2. **禁止盲目批量解决**：禁止使用 `git merge -X ours`、`git merge -X theirs`、批量 checkout 或批量 `accept incoming` 跳过审查。逐文件核实后，允许直接执行推荐的单文件方案。
3. **推荐方案直接执行**：每个冲突文件仍须逐一审查、解释并给出唯一推荐；常规情况直接执行，无需用户手动确认。只有特别复杂或涉及重大行为取舍时，才暂停相关操作并请求确认；不以文件、冲突、提交或代码行数设置确认门槛。
4. **可回滚**：合并全程在独立分支上操作，主分支不受影响，随时可丢弃。

## 执行与确认边界

以下规则统一适用于合并前预览、冲突解决、自动合并结果审查，以及新增和删除文件的处理：

- **常规情况**：调用方、类型、配置、依赖及 CHANGELOG 关联已核实，能证明推荐方案保留本地功能且满足跨文件契约时，说明唯一推荐及依据后立即执行。不得仅因出现冲突、关联 CHANGELOG、需要手动编辑或位于重点目录而要求确认。
- **特别复杂**：涉及多个模块的耦合重构，无法可靠判定本地与上游行为是否兼容；或需要在本地功能、安全语义、接口兼容性之间作实质取舍。先完成可独立进行的调查，再展示具体方案、影响及未决问题，请用户确认。
- **重大行为取舍**：涉及核心登录/权限语义改变、数据库破坏性迁移、重要接口或配置不兼容、本地功能删除等实际取舍时，须说明影响并请用户确认后继续相关操作。重点是能否证明兼容、保留本地功能及安全回滚；仅重构范围广或文件多，但行为兼容且验证充分时，仍直接执行推荐方案。不能通过拆分文件规避跨模块影响评估。
- **数量仅供汇报**：文件数、冲突数、提交数和代码行数只用于描述工作量与审查进度，不触发确认。大量机械性修改可直接处理；单个文件若涉及无法可靠判定的权限语义或数据迁移，也应请求确认。
- **证据不足**：先继续查证，不得把未经核实的方案标为推荐并执行；查证后仍无法可靠判断时，按特别复杂处理。
- **已有授权沿用**：用户已确认的范围和方案直接执行；没有新增重大风险或超出已确认范围时，不重复询问。对整体合并范围的授权不等于授权后续尚未说明的复杂取舍。
- **授权范围**：直接执行推荐方案包含文件编辑及 `git add`；提交、推送等操作仍依照用户在当前会话中的授权，不因本规则自动获得授权。

需要确认时，必须说明触发了哪一条边界，并给出具体文件、行为影响和可审查的方案。仅暂停依赖该决定的操作，可继续无依赖的调查与审查。

## 逐文件说明格式

1. **当前本地逻辑**：说明合并前本地版本现在怎样运行、提供什么二开功能，以及对应的 CHANGELOG 条目或本地不变量。这里的“当前”固定指合并前的本地方案，不得与 Git 自动合并后的暂存结果混淆。
2. **上游修改逻辑**：说明 `upstream/main` 相对共同基线具体新增、删除或重构了什么，以及它解决的问题或引入的跨文件契约。
3. **最终推荐**：先分别用相对精炼但信息完整的语言说明选择各方案后的实际运行逻辑和损失，再给出唯一的最终推荐：
   - **选择保留本地后**：最终文件怎样运行，以及会缺少哪些上游修复、功能或结构性改动。
   - **选择采用上游后**：最终文件怎样运行，以及会丢失哪些本地功能或破坏哪些二开不变量。
   - **选择手动合并后**：仅在双方逻辑可兼容时说明合并后的运行逻辑；若不适用，明确说明原因。
   - **最终推荐**：只推荐一个方案，并用一至两句话说明它为何最能同时满足本地功能保护、上游改动接入、编译和跨文件契约。

推荐必须建立在以上三项的真实对比上。若尚未核实调用方、类型、配置、依赖或 CHANGELOG 关联，不得先给推荐。不得把“推荐后的逻辑”拆成第四个并列主段落。

## 合并流程

### 第 1 步：准备（在合并前执行）

```bash
# 确保工作区干净
git status  # 必须无未提交的修改

# 确认 upstream remote 存在，不存在则添加
git remote -v
# 若无 upstream：git remote add upstream <上游仓库URL>

# 拉取上游最新代码（仅 fetch，不合并）
git fetch upstream

# 创建合并专用分支（从当前主分支创建）
git checkout -b merge/upstream-YYYY-MM-DD
```

### 第 2 步：预览上游变更（合并前必看，决定是否继续）

在执行合并前，先预览上游的变更量级和范围，按“执行与确认边界”决定直接继续或请求确认：

```bash
# 查看上游领先本地多少个 commit
git log HEAD..upstream/main --oneline | head -30

# 查看上游变更了哪些文件及变更量
git diff HEAD...upstream/main --stat

# 查看上游变更涉及哪些目录（粗略评估影响范围）
git diff HEAD...upstream/main --stat | tail -1
```

#### 2.1 交叉比对二开变更日志

读取 `changes/CHANGELOG.md`（及 `changes/details/` 目录下的详情文件），提取所有二开修改过的文件列表。将上游变更文件与该列表交叉比对，标出哪些二开功能会受上游更新影响：

- **冲突高风险文件**：上游修改了 CHANGELOG 中记录的二开文件 → 几乎必然产生冲突，提前预警
- **无影响文件**：上游修改的文件不在 CHANGELOG 中 → 通常可安全合并

向用户展示影响摘要，例如：

```
上游变更涉及以下二开功能：
  - #023 LDAP 登录（controller/ldap.go、service/feishu_sync.go）
  - #003 首页定制（web/default/src/features/home/...）
  - #013 主题预设（web/default/src/styles/theme-presets.css）
上游变更的其余 42 个文件未涉及二开修改。
```

将以上信息呈现给用户。常规情况说明推荐继续合并的依据后直接进入第 3 步；仅触发“特别复杂”或“重大行为取舍”边界时，使用 AskQuestion 确认：

- **继续合并**：进入第 3 步
- **放弃**：`git checkout main && git branch -D merge/upstream-YYYY-MM-DD`

可按功能与依赖关系分批审查以降低认知负担，但不得因数量多而额外请求确认，也不得拆散必须一起处理的跨文件契约。

### 第 3 步：执行合并（保留冲突标记，随后逐文件审查处理）

```bash
# 合并但不自动提交，冲突保留标记供逐文件审查
git merge upstream/main --no-commit --no-ff
```

- `--no-commit`：合并后不自动提交，留出审查窗口。
- **不使用** `-X ours` 或 `-X theirs`：冲突以标记形式保留，确保逐文件审查后再执行推荐方案。
- 上游的**新增文件**会被正常引入（无冲突），仍需审查。

### 第 4 步：分类所有变更文件

合并后先建立全局视图，将文件分为四类分别处理：

```bash
# 列出冲突文件（未合并状态）
git diff --name-only --diff-filter=U

# 列出已自动合并的变更文件（已暂存）
git diff --cached --name-status

# 列出上游新增的文件
git diff --cached --name-status --diff-filter=A
```

按以下优先级呈现给用户：

1. **冲突文件**（`U` 状态）→ 必须逐一走完冲突解决流程（第 5 步）
2. **已自动合并的修改文件**（`M` 状态）→ 审查 diff，按确认边界执行推荐方案
3. **上游新增文件**（`A` 状态）→ 审查内容及依赖，按确认边界决定是否保留
4. **上游删除的文件**（`D` 状态）→ 核实本地功能影响，按确认边界决定是否跟随删除

### 第 5 步：逐文件冲突解决（最关键，绝不可跳过任何一个）

对**每一个**冲突文件，必须严格按以下子步骤执行。常规文件逐一审查并连续执行推荐方案，不逐个等待用户回复。需要确认的复杂文件必须分别说明；相互依赖的跨文件方案可一并确认，但不得省略任一文件的分析。

#### 5.1 展示冲突上下文

使用 `git diff <file>` 显示冲突标记，清晰标注 ours / theirs 区域：

同时用 Read 工具读取文件完整内容，确保理解冲突的完整上下文。

#### 5.2 解释差异（中文）

用中文向用户清晰解释差异，并套用“逐文件说明格式”：

- **当前本地逻辑**：引用 `changes/CHANGELOG.md` 中的对应条目（编号和说明），解释二开增加/修改了哪些功能、为什么这样改
- **上游修改逻辑**：上游新增了什么功能、修了什么 bug、做了什么重构，并说明两者在哪些具体行或逻辑上产生分歧
- **最终推荐**：分别说明保留本地、采用上游和手动合并后的实际结果，再给出唯一推荐

如果冲突文件在 CHANGELOG 中有记录，**必须引用对应条目编号**，让用户快速关联到二开功能。例如：「本地改动来自 #023（LDAP 登录）和 #025（移除 User 表 name 字段），上游在此处新增了…」

#### 5.3 确定方案（只给一个最终推荐）

必须结合当前文件的真实差异，在三个方案中给出且只给出一个 **【最终推荐】**。常规情况说明后直接执行；仅触发确认边界时使用 AskQuestion 工具让用户选择处理方式。禁止同时出现“默认推荐”“实际推荐”“本文件建议”等互相竞争的推荐。

推荐必须基于可验证的技术结果：是否保留二开功能、是否纳入必要的上游修复或重构、是否能够编译，以及是否保持跨文件契约。不要因为固定模板而无条件推荐某一选项。

给出最终推荐时，必须先说明三个选项的实际运行结果，再说明推荐原因，至少覆盖：

- 推荐方案保留了哪些本地功能或二开不变量；
- 推荐方案纳入了哪些必要的上游修复、功能或结构性改动；
- 另外两个选项会分别丢失什么、破坏什么或引入什么风险。

不得只写“建议选 3”或“此文件建议手动合并”等无依据结论。原因必须针对当前文件和当前冲突，不得复用空泛模板。

按以下标准确定最终推荐：

- 双方逻辑独立且可以安全共存时，最终推荐通常应为**手动合并**。
- 上游会删除或破坏无法在本文件中兼容的二开功能时，最终推荐应为**保留本地**。
- 本地实现已被上游完整取代，且相关二开功能经核实仍能保留时，才可最终推荐**采用上游**。

三种方案的执行方式如下；需要确认时向用户展示三个选项，并只在最终推荐的选项上标记 **【最终推荐】**：

- **保留本地 (ours)**：保持二开的改动不变，丢弃上游在此处的变更
  → 执行 `git checkout --ours <file> && git add <file>`
- **采用上游 (theirs)**：使用上游的新版本，覆盖本地在此处的改动
  → 执行 `git checkout --theirs <file> && git add <file>`
- **手动合并**：AI 按已核实的方案用编辑工具合并双方逻辑；常规情况直接写入，触发确认边界时先展示拟合并的完整相关代码片段，用户确认后再写入
  → 编辑完成后执行 `git add <file>`

AskQuestion 中的选项说明不得过度压缩成“保留本地：不兼容”“采用上游：丢失功能”等短标签。每个选项都必须用一段适度精炼的完整描述，让用户不回看上文也能理解：

- 选择后文件最终怎样运行；
- 会保留哪项关键本地功能或纳入哪项关键上游改动；
- 会丢失什么、破坏什么或承担什么具体风险；
- 最终推荐项还必须在选项内简要说明推荐依据，并标记 **【最终推荐】**。

选项说明无需重复上文全部细节，但不能只给方案名称、抽象评价或编译结论。

在选项前必须完整给出“当前本地逻辑 → 上游修改逻辑 → 各方案实际结果 → 最终推荐”。例如：「**选择保留本地后**：LDAP 公司名称仍按本地规则迁移，但缺少上游计费表达式校验。**选择采用上游后**：获得上游校验，但丢失 LDAP 公司名称迁移。**选择手动合并后**：保留 LDAP 迁移，并让计费请求先经过上游新增的表达式校验。**最终推荐：手动合并**，因为它同时保留本地功能并纳入必要的上游校验。」选项标签中的【最终推荐】必须与这段结论一致。

#### 5.4 执行推荐或等待必要确认

- **常规情况**：直接执行 5.3 的唯一推荐方案，不调用 AskQuestion、不停下来等待回复。记录推荐依据和执行结果。
- **特别复杂或重大行为取舍**：展示具体方案及触发确认的原因，等待用户明确选择后再修改相关文件。待确认的冲突文件保持冲突状态，相关依赖变更一并暂缓。
- 用户已明确选择的方案按该选择执行；若执行中发现新增重大风险或必须改变方案，补充证据并针对新问题确认。

#### 5.5 标记已解决

推荐方案直接执行或用户确认的方案执行完成后，确保文件已 `git add`：

```bash
git add <file>
# 确认该文件不再出现在冲突列表中
git diff --name-only --diff-filter=U
```

#### 5.6 重复至所有冲突文件处理完毕

逐文件循环执行 5.1–5.5，并记录方案、执行依据（常规推荐直接执行或用户确认）与解决结果，直到 `git diff --name-only --diff-filter=U` 返回空（零冲突）。

### 第 6 步：审查已自动合并的文件

冲突文件全部解决后，还需审查那些 git 自动合并成功的文件（无冲突但有变更）。

**注意：git 自动合并成功 ≠ 结果正确。** 双方修改了同一文件的不同区域时 git 会自动合并，但合并结果可能在逻辑上冲突（编译通过但行为错误）。这比显式冲突更危险。

审查时需区分两种情况：

- **仅上游修改的文件**（本地无改动）→ 风险低，可批量审查 diff 并汇报，常规情况直接接受推荐结果
- **双方都修改过但 git 自动合并的文件**（本地也有改动）→ **高风险，必须逐一详细审查**

**CHANGELOG 关联文件必须单独审查**：即使 git 自动合并成功，凡是出现在 `changes/CHANGELOG.md` 条目或 `changes/details/*.md` 详情文件中的文件，均属于二开修改文件，必须逐一展示 diff 确认合并结果没有破坏二开功能。

每个自动合并文件也必须完整使用“逐文件说明格式”：先解释当前本地逻辑，再解释上游修改逻辑，然后分别说明保留本地、采用上游和手动调整后的实际结果，最后给出唯一最终推荐。不得因为 Git 没有产生冲突而省略任何一项。

对于每个需审查的文件，从以下方案中给出唯一推荐；常规情况直接执行，仅触发确认边界时让用户选择：

- ✅ 接受自动合并结果
- ❌ 回退到合并前状态：`git checkout HEAD -- <file>`
- ✏️ 在自动合并基础上手动调整

对于**本地独有目录**（见下方列表）中的文件，即使自动合并成功也**必须**逐一审查 diff，核实本地内容受到保护；是否请求用户确认仍按统一边界判断。

### 第 7 步：审查上游新增与删除的文件

- **新增文件**：逐一列出文件路径和内容摘要，核实依赖后给出推荐，常规情况直接执行。若新增文件路径与本地独有目录（`changes/`、`.cursor/`、`.agents/`）冲突，**必须警告用户并优先保护本地内容**；若兼容方案特别复杂或涉及重大行为取舍，再请求确认。
- **删除文件**：列出上游删除的文件，核实调用方和替代实现后决定是否跟随删除。若本地对该文件有二开修改，**默认建议保留**；常规情况直接执行推荐，涉及本地功能损失或无法可靠判断影响时请求确认。

## 禁止操作清单

| 禁止操作                                  | 原因                 |
| ----------------------------------------- | -------------------- |
| `git merge -X theirs`                     | 直接用上游覆盖本地   |
| `git checkout --theirs .`                 | 批量采用上游版本     |
| `git checkout --ours .`（批量，非单文件） | 批量跳过审查         |
| 在主分支上直接合并                        | 无法回滚             |
| 跳过 `--no-commit` 直接提交               | 没有审查窗口         |
| 批量 accept 所有 incoming changes         | 丢失本地改动         |
| 跳过任何一个冲突文件的审查                | 可能静默丢失二开功能 |
| 对特别复杂或涉及重大行为取舍的未授权方案直接执行 | 跳过必要的用户决策 |

## 本地独有目录保护

以下目录/文件是本地独有的，上游仓库中不存在。合并时若上游新增了同名路径，**必须立即警告用户并默认保留本地版本**：

- `changes/` — 二开变更日志
- `.cursor/` — Cursor IDE 配置与规则
- `.agents/` — Agent 技能与配置

## 合并后验证（第 8 步，不可跳过）

合并提交后，**必须**执行以下验证流程，确保没有遗漏上游改动：

### 8.1 编译验证

```bash
go build ./...
```

编译失败 = 有结构性遗漏（如新增函数被调用但未合并其定义）。**必须修复后才能继续。**

### 8.2 逐提交文件对比

对本次合并范围内的每个上游提交，逐一检查其涉及的文件是否在本地正确体现：

```bash
# 列出本次合并包含的所有上游提交
git log <prev-merge>..<current-merge> --oneline --no-merges --right-only upstream/main

# 对每个上游提交，获取涉及的文件列表
git show <commit-hash> --stat --name-only

# 对比每个文件的当前状态与上游
git diff HEAD upstream/main -- <file-path>
```

### 8.3 分类差异

对照 `changes/CHANGELOG.md` 判断差异是否属于已记录的二开改动。CHANGELOG 中有记录的差异 → 预期的本地定制；CHANGELOG 中无记录的差异 → 可能是合并遗漏，需重点排查。

| 差异类型                                                                                                 | 判定              | 处理     |
| -------------------------------------------------------------------------------------------------------- | ----------------- | -------- |
| 无差异                                                                                                   | ✅ 已正确合并     | 无需操作 |
| 差异对应 CHANGELOG 条目（如品牌重命名、主动移除的功能、UI 定制等）                                       | ✅ 预期的二开改动 | 无需操作 |
| **结构性/逻辑性改动缺失**（如函数签名变更、新增函数、重构等不在我们代码中），且不在 CHANGELOG 记录范围内 | ❌ **遗漏**       | 必须修复 |
| **新增文件在上游存在但本地不存在**（且不在 CHANGELOG 记录的主动移除范围内）                              | ❌ **遗漏**       | 必须修复 |

### 8.4 关键检查点

- **函数签名变更**：上游若修改了函数参数（如添加 `ctx context.Context`），所有调用方也必须同步更新
- **类型/结构体变更**：上游若重命名或新增字段，引用处必须同步
- **旧代码移除**：上游若删除了旧实现并替换为新实现（如用系统任务运行器替代 goroutine），本地也必须完成替换，不能保留旧实现
- **新增文件**：上游新增的 Go 文件、前端组件等必须检查是否正确引入
- **依赖变更**：`go.mod`、`package.json`、`bun.lock` 等依赖文件的上游更新需要正确合并
- **跨文件依赖**：文件 A 新增了函数定义，文件 B 调用了该函数。文件 B 无冲突被自动合并，但文件 A 的冲突解决时遗漏了函数定义

### 8.5 常见遗漏模式（必须重点防范）

以下模式在合并时极易被遗漏，需特别注意：

1. **冲突解决时选择保留本地，但上游改动包含必要的结构性重构**
   典型案例：上游将 `testChannel()` 添加了 `ctx` 参数并重构了调用链，冲突解决时保留本地版本导致新函数 `runChannelTestTask` 未定义、编译失败

2. **上游在同一文件中同时包含品牌重命名和功能改动**


3. **跨文件依赖断裂**
   文件 A（如 `system_task_handlers.go`）无冲突被自动合并，其中调用了新函数 `runChannelTestTask`。但定义该函数的文件 B（如 `channel-test.go`）有冲突，解决冲突时保留了旧版本，导致函数定义缺失

4. **上游删除旧实现但本地保留**
   上游移除了 `AutomaticallyTestChannels`/`testAllChannels` 等旧函数（因为功能已迁移到系统任务运行器），但冲突解决时保留本地导致旧代码残留、新旧实现并存

## 合并后复盘与上线交接（第 9 步，不可跳过）

合并提交创建并完成第 8 步验证后，必须完整读取并执行 `../upstream-merge-review/SKILL.md`，生成合并后复盘报告。若用户尚未授权创建合并提交，则保持当前安全停点，不得把暂存结果描述为最终合并结果。

复盘报告至少回答：

1. 本次上游有哪些改动；
2. 最终实际合并了哪些内容；
3. 影响到了哪些本地二开功能及最终状态；
4. 上线前需要关注哪些可观察行为变化和迁移要求；
5. 哪些部分仍需人工测试，包含前置条件、步骤、预期结果和失败判定；
6. 哪些自动验证已执行、哪些未执行或受阻。

复盘必须基于 merge commit 的两个父提交、共同基线、最终代码和 `changes/CHANGELOG.md`，不得只复述上游 commit message。报告默认只读，不得为上游同步或冲突解决新增二开 CHANGELOG 条目。

## 合并分支清理（第 10 步，不可跳过）

合并完成并将目标分支 `v1` 成功推送到 `origin/v1` 后，必须删除本次使用的旧合并分支，避免长期残留 `merge/upstream-*` 分支。

删除前必须同时确认：

1. 当前 `v1` 与 `origin/v1` 指向同一提交；
2. 本地合并分支的 tip 已包含在 `v1`；
3. 若存在同名远端分支，其 tip 已包含在 `origin/v1`；
4. 当前不在待删除的合并分支上。

```bash
# 确认 v1 已推送完成
test "$(git rev-parse v1)" = "$(git rev-parse origin/v1)"

# 确认本地与远端合并分支均已进入目标分支
git merge-base --is-ancestor merge/upstream-YYYY-MM-DD v1
git merge-base --is-ancestor origin/merge/upstream-YYYY-MM-DD origin/v1

# 先删除远端分支（若存在），再安全删除本地分支
git push origin --delete merge/upstream-YYYY-MM-DD
git branch -d merge/upstream-YYYY-MM-DD
```

- 只能使用 `git branch -d` 安全删除；如果 Git 判断分支尚未合并，禁止改用 `-D` 强制删除，必须先查明遗漏提交。
- 若同名远端分支不存在，可跳过远端删除，但仍须删除本地合并分支。
- 删除后使用 `git branch --list` 和 `git branch -r --list` 确认本地、远端引用均已消失，并在最终交付中记录清理结果。
- 尚未完成合并提交、复盘验证或 `v1` 推送时，不得提前删除合并分支。

## 最终输出与处理详情（每次交付必需）

无论已完成合并、仅暂存待提交，还是因复杂问题暂停，最终回复都必须自包含，让用户无需回看过程消息即可知道当前结果。已完成合并时结合第 9 步复盘报告汇总；尚未提交时基于合并前版本、上游版本及当前工作区说明阶段结果，不得冒充已完成的合并复盘。

最终输出至少包含以下内容；没有相关事项时明确写“无”或“不适用”，未验证的内容不得推断为通过：

1. **当前状态与范围**：说明合并来源与目标、相关提交标识、当前分支、是否仍有冲突，以及提交、推送和合并分支清理各自是否完成。数量可作为工作量摘要，但不能代替功能说明。
2. **实际合入内容**：按功能说明上游修复、新增能力及结构调整最终如何体现在本地；指出用户可观察到的前后行为、UI、接口或配置变化，并链接关键文件。
3. **本地二开功能状态**：列出受影响的 CHANGELOG 编号与功能，说明哪些完整保留、哪些做了兼容调整、哪些仍待处理，以及支持结论的代码或验证依据。不得只笼统写“本地功能已保留”。
4. **处理决策与未合入内容**：对冲突文件及双方都修改过的自动合并文件，逐一记录最终方案、采用理由、保留的本地逻辑、纳入的上游逻辑和未采纳内容的具体影响；标明是推荐直接执行还是用户确认后执行。说明有功能影响的新增/删除文件处理，以及主动放弃或延后的上游功能、修复和原因。
5. **验证证据与限制**：列出实际运行的构建、检查或测试及结果，区分通过、失败、未执行和受阻；说明验证覆盖范围、未解决问题与环境限制。编译通过不能等同于业务行为已验证。
6. **上线与人工验证事项**：说明必要的配置、依赖、数据库和部署调整；对仍需人工测试的关键行为给出前置条件、操作步骤、预期结果与失败判定。无迁移要求时明确说明。
7. **剩余事项与下一步**：说明待确认决策、待执行验证及尚未获授权的提交/推送等事项；若暂停，指出具体阻塞、推荐方案及需要用户决定的内容。不得以笼统的“已完成”掩盖未完成步骤。

正文先给结论和关键行为变化，再给处理详情。详情较长时可链接完整复盘报告或处理记录，但正文仍须保留关键取舍、未合入内容、验证限制和待办；不能只给报告链接或文件数量。报告不得作为上游同步的二开 CHANGELOG 条目写入。

## 异常处理

- **冲突文件较多**：按功能与依赖关系安排审查并汇报进度，常规推荐连续执行；只有具体方案触发复杂度或重大行为取舍边界时，才暂停相关操作请求确认。
- **上游有 breaking change**：先阅读上游 CHANGELOG/Release Notes，核实本项目是否受影响；涉及重要接口、配置或数据迁移的不兼容变化时，按确认边界处理。
- **合并后构建失败**：不要急于修复，先确认是上游引入的问题还是合并导致的冲突遗漏。
- **随时可放弃**：`git merge --abort` 或 `git checkout main && git branch -D merge/upstream-YYYY-MM-DD`。
