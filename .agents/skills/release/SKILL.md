# Casdoor 全自动发布

## 执行约定

- 用户调用 `/release`、`$release` 或明确要求全自动发布 Casdoor，即授权一次 Docker 发布，以及成功后对单个 Casdoor 实例的 1Panel 更新、强制拉取和重建，无需阶段间再次确认。创建、编辑或解释本技能时不触发发布。
- Casdoor 只有一套部署，不区分对内、对外，不提供目标选择，不要求 `target`，不读取 `targets.internal` 或 `targets.external`。
- Docker 阶段完整读取并执行 [docker-publish](../docker-publish/SKILL.md)。部署阶段按 [1Panel 单实例部署](references/1panel.md) 执行；该参考包含本项目的配置结构、鉴权、更新接口和核验规则。
- 默认仓库 `jahnli/casdoor`，工作流 `docker-publish.yml`；默认节点 `local`，编排、服务和容器名 `casdoor`，预期镜像仓库 `jahnli/casdoor`。用户指定值及本地部署配置优先；这些默认值是目标约定，不是镜像已发布的证据，实际编排及容器必须唯一匹配后才能更新。
- ref 使用用户指定的远端分支或标签，否则查询远端默认分支；reason 遵循 Docker 技能。只发布远端代码，不自动提交、推送、创建标签、创建 GitHub Release 或修改工作流。
- 顺序固定为“Docker 发布 → 核实镜像 → 1Panel 更新 → 核验 → 汇总”。不设置独立预检；Docker 成功且镜像核实后才读取 1Panel 凭据、查询部署配置。
- 使用 Docker 阶段实际产出的完整版本镜像，不使用 `latest`，不从本地版本、提交 SHA 或日期推算标签。不再询问镜像标签。
- 直接使用两个阶段的命令和 API，不生成临时脚本、包装脚本或额外实现文件；凭据、签名、Compose、env 和请求体只在请求进程内存中保留。不得展示凭据文件、完整响应、Compose 或未经脱敏的日志。
- 任一阶段失败或状态无法确认时停止后续写操作，保留已知运行和任务 ID。请求超时先查同一运行或任务，不自动重跑、不重复提交、不自动回滚。

## 1. 发布并核实 Docker 镜像

1. 按 Docker 技能确定 ref、记录触发前时间和已有运行 ID、触发一次工作流，定位本次唯一运行，再轮询同一运行直至完成。不提前查询登录状态、工作流状态或工作流定义。
2. 记录 `run-id`、运行链接、`headBranch`、`headSha` 和 `conclusion`。仅 `conclusion == success` 允许继续；失败、取消、跳过或结果不明时说明“1Panel 未执行”。
3. 从本次运行日志中的 `Building version:`、版本镜像标签和推送完成记录核实完整版本镜像及 digest（若有）。默认镜像标签来自远端构建中的 `git describe --tags --always`，不能用截短 SHA 代替完整标签。
4. 命名空间被脱敏时，不以 GitHub 所有者、预期仓库或 `DOCKER_USERNAME` 变量名作为发布仓库证据。可在成功后读取该次 `headSha` 的远端工作流，结合构建输出核实；也可用只读镜像清单查询，证明预期仓库的该标签 digest 与本次推送 digest 一致。不得查询或输出 secret 的值。
5. 完整仓库、标签或推送完成证据无法核实时报告“Docker 构建成功，部署阻塞：目标镜像未核实”，不更新 1Panel。实际仓库与预期目标不同也停止，不擅自替换仓库。

## 2. 更新单个 1Panel 实例

1. 将已核实的完整版本镜像交给 [1Panel 单实例部署](references/1panel.md)。在请求进程中读取根目录 `.1panel.local.json` 的顶层配置，不询问对内或对外。
2. 解析并校验配置，查询目标编排、Compose 和容器；记录原镜像、容器 ID、镜像 ID、状态和访问地址。缺少配置、目标不唯一或镜像仓库不一致时报告“Docker 发布成功，1Panel 部署阻塞”。
3. 简述面板 API 地址、编排、目标镜像及重建可能造成的短暂中断。仅修改目标服务镜像，保留其余服务、卷、env 和 Unicode 内容，生成唯一 `taskID`，提交一次 `forcePull: true` 的编排更新。即使标签相同也执行本次已授权的强制拉取和重建。
4. 轮询同一任务，最多等待 10 分钟，确认任务成功、镜像拉取成功、目标容器重建和启动。超时或结果不明时查询任务和容器，返回已确认现状，不重复提交。

## 3. 核验与完成判定

重新读取部署配置和容器，按部署参考核验：

- Compose 与容器 `Config.Image` 都是本次完整版本镜像。
- 新容器 ID 与原 ID 不同；记录新旧镜像 ID，同标签镜像 ID 可以不变。取得推送 digest 时，核对运行镜像对应的 RepoDigest；多架构镜像需核实索引与当前平台清单的关系，不直接比较不同层级的 digest。
- 容器为 `running`，有健康检查时等待 `healthy`，无健康检查时注明，并记录重启次数。
- 配置中的 `statusUrl` 指向 Casdoor `/api/health`，要求 HTTP 200 且 JSON `status == "ok"`。不使用 new-api 的 `/api/status` 或 `success == true` 判定。
- 如配置了 `versionUrl`，按参考核对 `/api/get-version-info` 的 `data.commitId` 与本次 `headSha`；`data.version`、`commitOffset` 与 Docker 标签可能格式不同，不直接比较字符串。未配置版本接口或接口不可用时，注明应用版本未核实及已确认的镜像证据，不宣称应用版本核验通过。

只有镜像、任务、容器及健康检查均通过才报告发布成功；配置了版本核验但未通过时，报告“部署完成，版本核验未完成”或实际不一致原因。健康接口仅证明存活，不声称登录、数据库或 OAuth 流程已验证。

所有轮询单次等待不超过 30 秒，每 60 秒内给出简短进度。健康检查仍为 `starting` 时按参考给出有限启动等待，不能立刻判为失败，也不能无限等待。

## 4. 最终交付

最终中文回复只列已核实信息，缺项写“未核实”或“未执行”：

```text
发布结果：成功 / 失败 / 阻塞 / 部署完成但核验未完成
Docker：结果；远端 ref；提交 SHA；完整版本镜像；digest（若有）
构建详情：GitHub Actions 运行链接（运行 ID）
1Panel：结果；节点与编排；任务 ID
容器：新短 ID；运行状态；健康状态；重启次数
应用：健康接口 HTTP 结果和 status；应用版本及提交核验结果（若配置）
访问地址：accessUrl（缺失或非法时写未核实）
健康接口：实际使用的 statusUrl
面板 API：实际使用的 baseUrl（非登录入口）
原镜像：更新前的完整镜像引用
```

地址和运行链接使用可点击链接。失败或阻塞时追加停止阶段、脱敏原因、当前服务状态和下一步所需操作；构建和部署结果分别说明。任何回滚需另有授权，并核实数据库迁移兼容性。

## 调用示例

- `/release`：发布远端默认分支，成功后更新唯一 Casdoor 实例并核验。
- `/release ref=<远端分支或标签>`：发布指定 ref，再用该次实际版本镜像更新实例。
- “全自动发布 Casdoor，先构建 Docker，成功后更新 1Panel”：执行同一完整流程。
