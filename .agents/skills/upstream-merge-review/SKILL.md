# 上游合并完成后的交接报告

复盘已完成的 upstream 合并，基于 merge commit、CHANGELOG 和最终代码，说明这次更新带来了什么，以及上线前需要关注什么。

## 复盘依据

1. 确定目标 merge commit，核实两个父提交分别对应合并前本地和上游版本，并找出共同基线。优先使用用户指定或当前会话明确的提交，无法确定时再询问。
2. 比较共同基线到上游、合并前本地到 merge commit 的差异，区分上游改动与实际合入内容。
3. 读取目标版本的 `changes/CHANGELOG.md` 和相关 `changes/details/`，结合最终代码及必要的调用方，核实二开功能受到的影响。

所有结论以目标提交为准，不用后续 HEAD 或工作区内容替代，不仅凭 commit message 或文件重叠作判断。合并尚未完成时，不生成最终交接结论。

## 报告内容

使用中文，先简述合并版本和总体结果，再按功能归纳：

1. **改动范围**：涉及哪些主要功能、模块和依赖。
2. **实际合入内容**：哪些完整接入、经过本地适配、保留本地实现或未合入，最终怎样运行。
3. **本地功能影响**：关联 CHANGELOG 编号，说明二开功能是否保留、增强或发生行为变化。
4. **UI 变化**：单独归纳用户可见的界面与交互变化，包括页面入口、布局、组件、文案、状态反馈、响应式行为和操作流程。说明变更前后差异、影响的角色或使用场景，以及最终界面采用上游实现、本地实现还是兼容适配；仅内部重构、测试调整或无可见效果的前端改动不得列为 UI 变化。若本次没有 UI 变化，明确写明“无用户可见的 UI 变化”。
5. **上线前行为变化**：说明使用者可观察到的变化、生效条件，以及必要的配置、兼容或迁移事项。

末尾简要补充已有验证结果、待确认问题和必要的人工验收建议。未执行的验证如实标记，不把构建成功当作业务验收通过。

## 边界

- 默认只读，不修改代码、CHANGELOG 或 Git 状态；发现问题记录证据与影响，不自动修复。
- 报告保持精简，附关键代码依据，不逐文件复述 diff，不重演冲突解决流程。
- 默认在回复中交付；用户要求保存时再写入指定位置。
