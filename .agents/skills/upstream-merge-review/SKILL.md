# 上游合并完成后的交接报告

复盘已完成的 upstream 合并，基于 merge commit、CHANGELOG 和最终代码，说明这次更新带来了什么，以及上线前需要关注什么。

## 复盘依据

1. 确定目标 merge commit，核实两个父提交分别对应合并前本地和上游版本，并找出共同基线。优先使用用户指定或当前会话明确的提交，无法确定时再询问。
2. 比较共同基线到上游、合并前本地到 merge commit 的差异，区分上游改动与实际合入内容。
3. 读取目标版本的 `changes/CHANGELOG.md` 和相关 `changes/details/`，结合最终代码及必要的调用方，核实二开功能受到的影响。

所有结论以目标提交为准，不用后续 HEAD 或工作区内容替代，不仅凭 commit message 或文件重叠作判断。合并尚未完成时，不生成最终交接结论。

## 交付格式

使用中文，先给结论和关键行为变化，再列（无则写"无"或"不适用"）：

1. **状态与范围**：来源、目标、提交标识、当前分支、剩余冲突，提交／推送／分支清理状态。
2. **实际接入内容**：按功能说明修复、新能力和结构调整，接口与配置变化，链接关键文件。
3. **改动范围**：涉及的主要功能、模块和依赖，区分上游变更范围与最终实际合入范围。
4. **UI 变化**：单独归纳用户可见的界面与交互变化，包括页面入口、布局、组件、文案、状态反馈、响应式行为和操作流程。说明变更前后差异、影响的角色或使用场景，以及最终界面采用上游实现、本地实现还是兼容适配；仅内部重构、测试调整或无可见效果的前端改动不得列为 UI 变化。若本次没有 UI 变化，明确写明"无用户可见的 UI 变化"。措辞与 `upstream-merge` 的 UI 项保持同步。
5. **二开功能状态**：受影响 CHANGELOG 编号、保留或兼容调整结果、待处理项、代码或验证依据。
6. **决策与未接入内容**：冲突及双方修改文件的方案、理由、保留与舍弃的逻辑、具体影响；标注直接执行或用户确认；重要新增／删除文件的处理。
7. **验证与限制**：构建、检查、测试的实际结果，区分通过／失败／未执行／受阻。编译通过不等于业务验证通过。测试是否允许执行遵循当前用户指令与项目规范，禁止或未执行时如实说明。
8. **上线与人工验证**：配置、依赖、数据库、部署要求；关键人工测试的前置条件、步骤、预期结果、失败判定。
9. **剩余事项**：阻塞、待确认决策、待执行验证、未授权操作及明确下一步。

功能结论以目标提交为准；当前分支、冲突、推送及清理状态按复盘时实查结果单独说明。决策、用户确认与既有验证结果须有会话、记录或实际执行依据，无法核实时明确标记，不能从最终 diff 推断曾获确认或验证通过。

交付内容直接文字输出，不另生成 Markdown 报告文件，也不以报告链接替代正文；正文须包含关键取舍、未接入内容、验证限制和待办。

## 边界

- 默认只读，不修改代码、CHANGELOG 或 Git 状态；发现问题记录证据与影响，不自动修复。
- 报告保持精简，附关键代码依据，不逐文件复述 diff，不重演冲突解决流程。
- 直接在回复中交付，不生成 Markdown 报告文件；仅在用户另行明确要求保存时写入指定位置。
